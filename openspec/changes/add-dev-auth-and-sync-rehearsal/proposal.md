# add-dev-auth-and-sync-rehearsal

## Why

Phase M (`migrate-canonical-backend-to-appwrite`) is the cross-surface "same data everywhere"
proof, and today it is 100% owner-gated: it needs the owner's phone, their Google account, and
live OAuth. But most of what M.4 actually proves — backfill parity, per-entity dual-write →
dual-read cutovers, LWW conflict resolution, tombstones, note-entry sync — is **sync
architecture**, not Google plumbing. The locked user model ("any sign-in gets an isolated
per-user space") means a dedicated dev account (**user #0**) can rehearse every one of those
scenarios against the live project without touching the owner's data and without the OAuth
device dance.

Two concrete gaps block that rehearsal today:

1. **No non-Google session path.** `AppwriteAuthService` exposes only `signInWithGoogle`;
   there is no way to establish a session from a scripted/dev context.
2. **No hand on the M.4 switches.** The per-entity cutover prefs
   (`SyncService.movesDualWritePrefKey` et al.) are SharedPreferences bools flipped **only by
   tests** — no runtime surface flips them. As written, even the owner's real M.4 pass has no
   way to "flip the prefs" on a device. This change closes that gap for both the rehearsal and
   the real pass.

The smoke driver is already ruled: **argent** (`software-mansion/argent` v0.15.0, ruled
2026-07-13 in the launch wave). L3 used the chrome-devtools fallback only because the wave
preamble fenced `argent init` (writes repo config) — and explicitly fenced the full interactive
click-through "to argent / the Phase-M device pass". This change is that fenced work; it
sanctions `argent init` here.

## What Changes

- **Dev email/password auth seam** (flag `kDevEmailAuthEnabled`, dart-define
  `DEV_EMAIL_AUTH`, default **OFF** → release builds byte-identical): one new gateway method
  (`createEmailPasswordSession`) on the existing `AppwriteAccountGateway` seam, one service
  method (`signInWithEmailPassword`), and a flag-gated sign-in form on the auth screen.
  **Sign-in only — no registration UI or client-side `account.create`** (the product is
  invite-gated; user #0 is minted owner-side via `appwrite users create`).
- **R8 video-pointer rung + D8 OAuth findings** (2026-07-14 update): the rehearsal ladder
  gains a video **pointer** sync rung (bytes stay fenced to Phase M — user #0 has no
  Google/Drive account), and design D8 records the live-verified Google OAuth chain
  (Appwrite→Google green server-side via curl) so a failed device tap never restarts an
  OAuth debugging loop or blocks the ladder.
- **Dev sync-cutover panel** (flag `kDevSyncPanelEnabled`, dart-define `DEV_SYNC_PANEL`,
  default **OFF**): a runtime surface that reads/flips every per-entity dual-write / dual-read
  pref and shows current sync state. Serves the rehearsal AND the owner's real M.4 pass.
- **argent rehearsal harness**: `argent init` config committed; a scripted rehearsal
  (`docs/sync-rehearsal-runbook.md`) that drives user #0 through the exact M.3/M.4 scenario
  ladder on iOS simulator + Chromium web, with evidence recorded per scenario.

## Capabilities

- `dev-auth` — flag-gated email/password session path (sign-in only, isolated user space).
- `dev-sync-controls` — flag-gated runtime panel over the per-entity cutover prefs.
- `sync-rehearsal` — argent-driven cross-surface rehearsal of the Phase-M scenario ladder,
  with an honest fence around what it cannot prove.

## Non-goals

- **Not a replacement for Phase M.** The rehearsal cannot prove: live Google OAuth on iOS
  (M.2), the Drive token / Drive-video-on-web half of M.4, the legacy-identity claim (3.4 —
  joins on the Google email), remote-config flip on the owner cohort (M.5), or httpOnly web
  **OAuth** (M.6). Those stay owner-run; the ledger records them as fenced.
- **No public registration.** No client-side account creation, ever — invite-gated product.
- **Not the continuous E2E matrix.** `harden-marathon-reliability` owns the 3-platform E2E
  suite (backlog #5, wave-1 invite gate). This change is the one-shot rehearsal + the dev
  seams that suite can later reuse; it must not grow into a test framework.
- **No new backend surface.** Appwrite's built-in email/password session API only; no new
  tables, no Function changes.
