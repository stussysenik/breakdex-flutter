# Design System

`docs/design/TOKENS.md` is the single source of truth for every design token in this
codebase. This chapter does not restate those values — it **indexes** that file and adds only
what the source table cannot express: the conformance contract between the token file and its
consumers, and the **motion doctrine** that constrains which tokens a product surface may
touch. Read `../design/TOKENS.md` first; read this for the rules around it.

The runtime tokens live in `lib/core/design/` — twelve files. Most are `abstract final class`
namespaces of `static const` (or `static final`) members; the four colour files are not, and
the difference is the point (see **Color is a vocabulary plus a derived ramp** below):

| File | Namespace(s) |
| --- | --- |
| `colors.dart` | `AppColors` — pack **data**, not the vocabulary |
| `color_roles.dart` | `AppColorRole`, `AppColorRoleKind` (enums — the closed color vocabulary) |
| `color_packs.dart` | `ColorPack`, `ColorPackId`, `ResolvedColors` (the swappable resolution) |
| `color_catalogue.dart` | `ColorCatalogue`, `ColorCollection`, `InHouseCatalogue` (discovery layer) |
| `oklch.dart` | `OklchColor`, `ColorRamp`, `rampFromSeed` (perceptual ramp derivation) |
| `contrast.dart` | `contrastRatio`, `relativeLuminance`, `meetsContrast` (WCAG readability) |
| `icons.dart` | `AppIcon` (enum), `IconPack`, `AppIconPackTheme`, `AppIconView` |
| `spacing.dart` | `AppSpacing`, `AppRadius`, **`AppMotion`** |
| `layout.dart` | **`AppLayout`** (band geometry, clamps, vertical rhythm) |
| `typography.dart` | `AppFontFamily` (enum), `AppTypography` |
| `depth.dart` | `AppDepth` |
| `theme.dart` | `AppShadows`, `AppSemanticTheme` (the `ThemeExtension`) |

## Primitives

**Token.** A single named design decision — a color, a length, a duration, a curve, a type
style — exposed as one `static` member of an `AppX` namespace. A token is *canonical*: the
Dart constant **is** the value, not a copy of one. `AppSpacing.md` is `16.0`; there is no
prior authority it derives from. `TOKENS.md` is the human-readable registry of these
constants, not their origin.

**The grid.** All spatial tokens (`AppSpacing`, `AppRadius`) are logical-pixel multiples of an
**8pt base** with a **4pt half-step**. The ladder is `4, 8, 12, 16, 24, 32, 48, 64`
(`AppSpacing.xxs … xxxl`), plus `screenEdge = 24`. Every gap, pad, and inset a product surface
uses resolves to one of these — a raw numeric literal that equals a token value is a
conformance violation, not a shortcut.

**The frame.** The grid says how big a gap is; it does not say where anything goes. Placement
is a separate ruling — the **stacked-viewport model** (`AppLayout`): four bands, of which only
the content band varies, so content's first pixel lands at safe-area top + 80 on every screen.
It is enforced by a type, `AppScreen` (`lib/shared/widgets/app_screen.dart`), not by
convention: a screen that builds its own `Scaffold`, `AppBar`, or `SliverAppBar` has opted out
of the frame and is a review violation, on the same footing as a raw `Duration` in motion. The
four-band diagram, both token tables, and the one-scroll rule live in `../design/TOKENS.md` →
**Layout & Grid**.

**The basis is a value, not a constant** (ruled 2026-08-01, §5.1). Five of `AppLayout`'s
numbers — `gutter`, `baseline`, `blockGrid`, `rowHeight`, `headerHeight` — are also carried by
`AppLayoutTheme`, a `ThemeExtension` whose defaults *are* those constants. Layout code reads
`AppLayout.of(context)`, so a subtree wrapped in a `Theme` re-flows onto a different basis on
the next frame, with no hot restart and no edited source; with no extension registered the
lookup returns the constants, so a widget test that builds a bare `MaterialApp` measures the
shipped frame. This is the one place a token is not simply its constant — deliberately, because
a grid you can move a slider on is a grid you can *see*, and that gallery (§5.2–5.3) is what
the extension exists to serve. The other `AppLayout` members stay constants: five numbers
decide the grid, and every additional knob is one more thing that can disagree with itself.

All five tabs are on the frame as of 2026-07-29, so the migration ledger that tracked them is
retired; the roster now lives in `test/design/frame_conformance_test.dart`, where CI can fail
it. Anything the frame must do for a screen belongs to `AppScreen` rather than to the screen —
that is how `AppScreen.floatingActionButton` arrived, carrying with it the nav-band inset five
screens had each hand-rolled as `kBottomNavigationBarHeight + padding.bottom`.

**Detail routes joined the roster on 2026-08-01**, and the ruling that let them is worth
stating: they are pushed *inside* the shell branch, so band 4 was never absent — the only
missing fact was a way back. `AppScreen` now reads that from the route (`Navigator.canPop`)
rather than taking it as a flag, so a tab root cannot show a back control that would do
nothing and a pushed screen cannot forget one. The control is a chevron and no word, sized
`AppLayout.backSlot` (48): the crumb line directly above it already *says* where back goes,
and typing that twice is two things to keep in sync. Band 2 does not grow to hold it —
16 + 4 + 48 = 68 still fits inside the unchanged 72 — and because the header column is
centred, the title's centreline does not move between a tab root and a detail screen.
`BackLeading`, the labelled `AppBar` control three screens had each grown their own version
of, was deleted in the same commit: it existed only because detail routes built their own
chrome.

**Band 4 is a scope, not an assumption.** Settings joined the roster on 2026-08-01 and brought
the first screens pushed on the **root** navigator, where the shell — and its nav band — is not
above them at all. `NavBandScope` (`lib/shared/widgets/nav_band_scope.dart`) is an
`InheritedWidget` the shell wraps its branch navigator in; a root-navigator route is a *sibling*
of the shell in the root stack rather than a descendant, so it never finds the scope and is told
the truth. Presence *is* the value — the widget has no field, because the only question a
surface ever has is whether a band is drawn over it, and asking the tree cannot drift from the
router the way a hand-kept route list would. `AppScreen.bottomInsetOf` is therefore a sum,
`bandInsetOf + contentBottomGap + padding.bottom`, which named the 16 that had been hiding
inside `scrollBottomInset`: the trailing gap mirrors `contentTopGap` and is owed on every
route, the 56pt band only where one exists. `showAppSheet` reads the same scope, so a sheet
opened from Settings no longer floats above its own bottom edge. `SettingsScreen.isTab` was
deleted with it — one widget serves `/settings` and `/settings-panel`, and the route already
knows which is which.

**A dialog is bounded by a measure, not by the band.** `showAppDialog`
(`lib/shared/widgets/app_dialog.dart`) is the sheet helper's opposite number and deliberately
does *not* mirror it: `showDialog` defaults to the **root** navigator, so a dialog route is a
sibling of the shell and paints *over* band 4 — reserving space for it would be reserving space
for nothing. Height is Material's already (`Dialog` carries its own `SafeArea`), and a second
clamp could only re-introduce the double-counted safe inset `showAppSheet` had to remove padding
to avoid. What Material does not bound is width: its only lever is a 40pt `insetPadding`, so a
two-sentence confirm box on a 1400pt browser window is painted 1320pt wide. The helper clamps the
layout box to `AppLayout.dialogMaxWidth` (480); the gutter sits inside it, so the card is at most
400pt — the same card a 480pt phone gives it. The one exception carries its reason inline:
`Dialog.fullscreen` (the photo viewer) is a screen wearing a route and has no measure to keep.

**The roster became a closed table on 2026-08-01 (§4.4).** `frame_conformance_test.dart` was a
list of migrated screens — an allowlist, which can only ever say something about the files it
already knows. It is now four tables that partition *every* file under `lib/` that builds
chrome: `_onFrame` (through `AppScreen`, asserted chrome-free), `_frameless` (no bands at all,
on purpose, and never an `AppBar` — that is the band that drifted five times), `_awaitingRuling`
(still bespoke, one line each naming the *decision* owed rather than the typing), and
`_framework` (`app_screen.dart` and `bottom_nav_shell.dart`, the two files allowed to build
bands). A closure test walks `lib/` and fails on any chrome-building file in no table, so a new
bespoke `Scaffold` fails on the commit that adds it. That is already the denylist task 4.5 asks
for; 4.5 is now finished by *deleting* `_awaitingRuling` once it empties. Five screens joined
`_onFrame` in the same commit — auth, party, move-analysis, create-combo, and the dev sync
panel — and each states which of the three forms it takes and why in one comment above the
call. Two rulings fell out of migrating them: `create_combo` had a *tappable title* that
renamed the combo, and since the frame renders titles as text the rename became an action, next
to every other verb; `party` built a separate `Scaffold` in each of its loading, error and data
branches, so its header appeared and vanished as data resolved — on the frame the bands are
already there and only the fill changes.

**The address line lives inside band 2, which does not grow.** `AppBreadcrumb`
(`lib/shared/widgets/app_breadcrumb.dart`) renders the route as one line of type above the
title — `AppLayout.crumbHeight` (16) + `crumbGap` (4) + the 36pt title = 56, centred in the
unchanged 72pt header band. A header whose height changes between screens is precisely the
discontinuity `AppScreen` exists to remove, so the crumb was fitted into the band rather than
added to it.

**The type baseline.** Line heights ride **2pt** (`AppLayout.typeBaseline`), half the 4pt
layout baseline — owner's ruling, 2026-07-29. A productive ramp needs a heading step between
26 and 32, which a 4pt grid cannot express, so type gets the finer grid while *blocks* keep
the 8pt block grid. `titleMedium` (30) and `titleSmall` (26) sat in TOKENS.md as "known
non-conformance" until this ruling; they were conforming to a rule nobody had written down.
`test/design/type_baseline_test.dart` now fails if any step resolves to an odd line box.

**Type.** **Inter** is the default family. The static `AppTypography` scale
(`titleLarge … labelSmall`) hardcodes `fontFamily: 'Inter'` and follows the IBM Carbon
productive ramp (`12/14/16/20/24/32`). `AppFontFamily` is the user-selectable axis
(`inter · outfit · poppins · spaceMono · jetBrainsMono · system`); `AppTypography.textTheme(...)`
rebuilds the whole `TextTheme` for a chosen family, while the static getters stay Inter for
call sites that render before the theme resolves.

**Motion family.** Every visible product animation belongs to **exactly one of two
families**, and both are composed from `AppMotion` tokens:

- **Fluid** — the default. Animates **opacity and translation only**. Flow transitions ride
  `AppMotion.fluid` (an alias of `productive` = `Curves.easeInOutCubic`); appearances ride
  `AppMotion.entrance` (`easeOut`). Durations sit in the `fast01`–`moderate02` band.
- **Morph** — continuity of **one persistent identity** as its size/shape/position changes.
  Reserved for the state change of a *single* element (a panel expanding, a card reordering).
  Rides `AppMotion.morph`, an alias of `springGentle`, over `moderate02`. **Shared elements go
  through `AppMorph` and nothing else** (`lib/shared/widgets/app_morph.dart`): a raw `Hero`
  interpolates its rect linearly against the route's animation, which is the Fluid feel applied
  to a Morph problem, so `AppMorph.morphRectTween` spends the flight's own `t` on
  `AppMotion.morph` first. `test/design/morph_conformance_test.dart` bans a raw `Hero(` under
  `lib/` with no allowlist.

**Gotcha — a `Hero` in a page's `transitionsBuilder` is never found.** `ModalRoute.subtreeContext`,
the context Flutter searches on push, points at `buildPage`'s output only; everything
`buildTransitions` wraps around it is outside. The route just fades, with no error. `morphPage`
therefore puts the destination end in `MorphDestination` on the page's *child*.

**Gotcha — a spring curve is normalised onto its own settle time** (`isDone`, 1ms resolution,
3s ceiling). Until 2026-08-02 `_SpringCurve` used a fixed 3-second window, so `springGentle`
reached 1.0 at about `t = 0.2`: a 240ms transition showed ~40ms of motion and read as a pop.
If a spring ever looks instant, check what window it is sampled over before reaching for a
longer duration.

**`AppMotion`.** The motion namespace (in `spacing.dart` — see gotcha below). It holds the
duration ladder (`fast01 = 70ms … slow01 = 400ms`), the named curves, the two spring curves,
the two family aliases, and the three **ambient** durations that sit *outside* the two
families (`shimmerLoop`, `loaderLoop`, `celebrate` — loops and one-shot celebrations, not
transitions).

## Reasoning from the primitives

Four invariants follow directly:

1. **One value, one authority.** Because the Dart constant *is* the token, there is no drift
   between "the spec" and "the runtime" for Dart consumers — the spec is generated *from* the
   constants. `TOKENS.md`'s Dart column is therefore normative; its CSS column is aspirational
   (see invariant 4).
2. **Grid conformance is decidable.** A spatial literal is legal iff it is off-scale by intent
   or resolves to a token. `EdgeInsets.all(16)` is a violation (it equals `AppSpacing.md`);
   `EdgeInsets.all(15)` is a design decision to justify or snap. Reviews decide this
   mechanically for the on-scale case ([`#grid-1`](./09-standards.mdx#grid-1)).
3. **A raw `Curve`/`Duration` on a product surface names its own family — badly.** The two
   families exist so that motion is *legible from the call site*: reading `AppMotion.morph`
   tells a reviewer "this is shape continuity of one element." A bare `Duration(milliseconds:
   240)` or `Curves.easeInOutCubic` erases that classification and is a review violation
   ([`#motion-1`](./09-standards.mdx#motion-1)).
4. **CSS conformance is a contract, not a fact.** `web-mirror/`'s `tokens.css` is **planned,
   not present** — every CSS-property cell in `TOKENS.md` reads `(planned)`, and no
   `tokens.css` file exists in the repo today. When it lands it must mirror the Dart constants
   1:1 (the same relationship the XState web machines have to Flutter machines — [State
   Architecture](./02-state-architecture.mdx#the-web-mirror-rule)). Until then, "both conform
   to `TOKENS.md`" describes the intended invariant, not the current tree. **`AppLayout` is
   carved out of that contract** (ruled 2026-07-29): the stacked viewport is a claim about
   switching tabs in the shipped app, and `web-mirror` is an owner-only tool with no tab bar.
   Value tokens still aim to mirror; the frame does not.

## The motion doctrine, encoded

The doctrine is not a convention note — it is compiled into the token surface. From
`lib/core/design/spacing.dart`:

```dart
// --- Motion families (doctrine) ---
// Reference these aliases so the family a call site belongs to is legible.

/// **Fluid** default curve — flow transitions (opacity/translation). Alias
/// of [productive]; appearances use [entrance] instead.
static const Curve fluid = productive;

/// **Morph** curve — continuity of one persistent identity. Alias of
/// [springGentle].
static final Curve morph = springGentle;
```

The aliases carry no new numeric value; they exist purely to make the *family* readable at the
call site. `fluid` and `morph` point at `productive` (`easeInOutCubic`) and `springGentle`
respectively, so choosing a family and choosing a curve are the same keystroke.

**The delight budget.** Overshoot curves — `AppMotion.expressive` (`easeOutBack`) and
`AppMotion.springBouncy` — sit outside the two families. They are permitted *only* with a
justified call-site comment ([`#motion-2`](./09-standards.mdx#motion-2)); they are for
checkmarks, FAB entrances, card flips — moments that earn a "pop," never default flow.

**Ambient durations.** `shimmerLoop` (1200ms), `loaderLoop` (800ms), and `celebrate` (1500ms)
are named in `AppMotion` precisely so that loops and celebrations — which are neither Fluid nor
Morph transitions — still never introduce a raw literal onto a product surface. The signature
two-dot `AppLoader` is the canonical Fluid-family loading motif: two dots translate in opposite
phase on `fluid` and cross at center, one `loaderLoop` per half-sweep.

**The springs are real physics.** `springGentle`/`springBouncy` are not eased Béziers — they
wrap a `SpringSimulation` mapped onto Flutter's `0→1` `Curve` contract:

```dart
class _SpringCurve extends Curve {
  _SpringCurve(final SpringDescription spring)
      : _simulation = SpringSimulation(spring, 0, 1, 0);
  final SpringSimulation _simulation;

  @override
  double transformInternal(final double t) =>
      _simulation.x(t * 3).clamp(0.0, 1.0); // 0→1 curve param treated as 0→3s
}
```

The curve parameter `0→1` is stretched to `0→3` seconds (long enough for any reasonable spring
to settle) and the output is clamped to `[0, 1]` — the clamped overshoot is the visible bounce.

## Radius conformance and the pill idiom

`AppRadius` shares the grid (`4, 8, 12, 16, 24, 32`) plus `pill = 500` (fully round). A
`BorderRadius.circular(N)` whose `N` equals a token is a violation, resolved from the named
token; the fully-round idiom `circular(999)` maps to `AppRadius.pill`. Off-scale bespoke radii
that no token expresses are the exception — snapping them to the grid is a design decision, not
a mechanical swap ([`#token-1`](./09-standards.mdx#token-1)).

## Iconography is a vocabulary plus a swappable pack

Icons follow the same shape as every other token axis: a closed vocabulary the product speaks,
and an interchangeable implementation behind it. `lib/core/design/icons.dart` holds all four
pieces, and the split is the point — **a screen names a meaning; a pack chooses the glyph.**

- **`enum AppIcon`** — 80 semantic names. Every name states a meaning a surface can articulate
  (`back`, `empty`, `delete`); none describes stroke, weight, or terminal. Adding a name means
  adding a case in every pack in the same commit.
- **`abstract class IconPack`** — `resolve(AppIcon) → IconData`, implemented as a `switch` with
  **no `default`**. Dart's exhaustiveness check turns an incomplete pack into a compile error, so
  completeness is proven by the compiler rather than asserted in review. This is the same
  reasoning as the conformance tests below, moved one layer earlier: a gate that runs at
  type-check time beats a gate that runs in CI.
- **`enum IconPackId`** (`cupertino`, `material`, `lucide`) — the persistence key (`icon_pack` in
  SharedPreferences) and the factory. `fromKey` tolerates unknown values and falls back to
  `cupertino`, so removing a pack never bricks a client that persisted its name. **`cupertino` is
  the default**: a client that has never chosen a pack gets one vocabulary on every OS, rather
  than a glyph set that changes shape when the same build runs on iOS.
- **`AppIconPackTheme`** — a `ThemeExtension` carrying the resolved pack, registered by
  `AppTheme.light/dark(iconPack:)` alongside `AppSemanticTheme`. `AppIconPackTheme.of(context)`
  falls back to `MaterialPack()` when the extension is absent, so a widget pumped outside the app
  theme still renders.
- **`AppIconView(AppIcon.x)`** — the only sanctioned way to draw an icon. It reads the pack from
  the ambient theme, which is what makes a pack swap a theme change rather than a refactor.

**Raw `Icons.*` / `CupertinoIcons.*` anywhere under `lib/` outside `icons.dart` is a
violation**, enforced by `test/core/design/icon_conformance_test.dart` with a **zero-length
allowlist** — the absolute form, chosen because an allowlist is where this class of rule goes to
die. `test/core/design/icon_pack_test.dart` covers resolution and pack identity. The migration
that established it eliminated 434 raw call sites; the collapse ledger (where several Material
glyphs fold into one semantic name) lives in `../design/TOKENS.md` → Iconography, not here.

Two consequences worth stating, because both have already bitten:

- **A test must assert the semantic icon, not the glyph.** Asserting a specific `IconData` binds
  the test to whichever pack happens to be active, so it fails the moment a pack is swapped —
  the reason `test/helpers/icon_finders.dart` exposes `findAppIcon`.
- **A pack is a real dependency of the preview scaffold.** Adding `lucide_icons_flutter` for the
  Lucide pack invalidated the widget-preview scaffold's resolved package set, and every preview
  failed to compile until it was regenerated
  (`add-web-first-release-and-monetization` 1.0.6).

## Color is a vocabulary plus a derived ramp

Color is the one token family that is **not** canonical as a constant, and that break is
deliberate. `AppSpacing.md` *is* `16.0` — there is no prior authority. A color is different: a
screen never wants `#1F5EFF`, it wants "the one colored mark on this surface". So color has two
layers, and only the lower one is data.

**The vocabulary is closed.** `AppColorRole` (`color_roles.dart`) is 17 roles, each a thing a
screen means. The 39 constants in `colors.dart` are one pack's worth of *values*, not the
vocabulary — `lightBg`, `darkBg`, `monoLightBg`, and `monoDarkBg` are four values of the single
role `background`, resolved by brightness and by the accessibility overlay. Every role carries
an `AppColorRoleKind` (`surface` · `ink` · `signal`) naming which axis owns it, which is what
makes the overlay's *selective* override checkable rather than conventional. Same mechanism as
iconography above, and for the same reason: an exhaustive `switch` over a closed enum needs no
`default`, so an incomplete pack is a compile error, not a fallback color at runtime.

**Weights are derived in OKLCH, not listed as hexes.** `rampFromSeed` (`oklch.dart`) takes a
seed to a weight ramp. HSL would have been free; it is wrong here, and the reason is measured
rather than asserted (`test/core/design/oklch_test.dart`): yellow and blue at HSL `L 0.5`
differ by more than **0.3** of the visible lightness range, while at OKLCH `L 0.6` they differ
by less than **0.01**. The consequence is load-bearing — step *n* of any two hues is the same
weight, so "the step that clears 4.5:1" is a property of the ramp instead of a per-color
accident, and a contrast gate can be written once for every hue.

Gamut handling encodes the same priority: a step outside sRGB **spends chroma, never hue**
(bisection to the largest in-gamut chroma at fixed lightness and hue). Clipping RGB channels
would rotate hue, which is the one guarantee a ramp makes. The conversion is ~140 lines of
Ottosson's matrices with **no package added** — two matrix multiplies and a cube root each way
does not clear the essentialist bar for a dependency.

**A pack is `Color resolve(role, brightness)`, and deliberately nothing more.** It could have
been a `(ColorScheme, AppSemanticTheme)` factory — the same information — but then a pack would
know Material's slot names and could reach past its own axis. `ResolvedColors` is the seam:
pack plus per-role overrides go in, role-addressed colors come out, and only `AppTheme` maps
roles onto `ColorScheme` afterwards. Roles stop existing at exactly that line.

The wiring reads axis by axis, which is what made `_build` shrink rather than grow: the six
surface parameters (`bg`/`card`/`fill`/`text`/`secondary`/`separator`) and the hand-rolled
`gray ? mono… : light…` ternaries at every call site are **gone**. The grayscale modes now
express themselves as a *pack substitution* — `monoOutline` or the `monochrome` overlay
substitutes the `mono` pack — so one concept replaced two branches. Overrides are dropped in
those modes: a guarantee the user asked for outranks a preference they expressed earlier, and
nothing is erased. The substitution is now total — the one `copyWith` exception that re-stated
`error`/`onError` on top of it existed only to preserve the hardwire 2.4 removed, and the `mono`
pack already resolved both roles correctly on its own.

**Unset must mean "use the pack".** `AppTheme`'s colour parameters are nullable for that
reason, and it is not cosmetic: `accentColorProvider`, `learningStateColorsProvider`, and
`ratingColorsProvider` each bake the `AppColors` fallback into their own state, so they cannot
express "unset" — every read returns a colour. Feeding them straight into a theme would
override whichever pack is selected with the classic values on every build, and choosing `mono`
would leave the state pills pink. `colorRoleOverridesProvider` omits unset roles instead, and
reads the *same preference keys* those three write, so there is one stored truth per role and
no migration for a user who set an accent before packs existed.

**Contrast is gated, and it does not live in `oklch.dart`.** `contrast.dart` implements WCAG
2.1 relative luminance; keeping it separate is a correctness decision, not tidiness. OKLab
lightness is a *perceptual* quantity fitted to how a colour looks; WCAG luminance is
*photometric*, with different coefficients and a different transfer function. They disagree, so
deriving one from the other would return plausible wrong numbers. `accessible_palette_test.dart`
runs every pack × both brightnesses: **4.5:1** for text and for ink-on-accent, **3:1** for
signals on `card`/`background` — 3:1 rather than 4.5:1 because no signal carries meaning alone.

The split that makes that gate safe: **a pack we ship must pass; a user's override need only be
shown.** Our failing pack is our defect and fails CI. A user's own adjustment failing is their
informed choice — the picker displays the live ratio and accepts the value either way, because
WCAG is a legibility floor, not a universal aesthetic rule.

Two measured facts are recorded rather than gated, both in the shipped palette: `separator` on
`background` is **1.27:1** in classic light, which is the hairline doctrine working as intended
and WCAG-exempt as decoration; and `actionEasy` on `fill` is **2.98:1**, short of 3:1 by 0.02
(`add-color-packs` 4.5). Neither is gated because gating the first would fail the design
doctrine and the second would move a shipped hex, which is a design call.

Full role table, precedence rule, and the derived-weights ruling:
`../design/TOKENS.md#color-packs`.

## Accessible palettes are an orthogonal axis

Color is selected on three independent axes: theme brightness (light/dark), viewing mode
(`mono*` grayscale), and `AccessiblePalette` (`standard · deuteranopia · monochrome`). The
deuteranopia ramp is Okabe–Ito, applied to app-controlled semantic signals (learning states +
review ratings) only; surfaces and accent are untouched. Selection is **non-destructive** — a
user's accent/state/rating colors survive in prefs and return exactly when the palette is set
back to `standard`. Critically, **color is never the sole carrier of meaning**: rating buttons
pair color with a distinct icon *and* label (WCAG 1.4.1), state pills pair color with a label.
Full ramps are in `../design/TOKENS.md#accessible-palettes` — not duplicated here.

Once packs are selectable the three axes need an order, and it is fixed: **`pack → brightness →
AccessiblePalette overlay`, overlay last and winning.** Any other order is a silent regression
of this section — a user on `deuteranopia` picks an attractive pack and quietly loses the
Okabe–Ito guarantee the palette exists to provide. The `signal` kind on each role is how "the
overlay replaces meaning-by-color and nothing else" is expressed in code rather than in prose.

**The hole in that axis is closed, and the closing taught three things** (`add-color-packs`
2.5, 2026-07-30). The chapter used to record 241 raw `AppColors.*` reads in 58 files bypassing
the overlay — `milestone_list.dart:292` keeping the unsafe `#1F8A70` under deuteranopia was the
confirmed case. The gate was written first and found **275 sites in 55 files**: the figure had
grown, because Phase 5 shipped a new settings surface into the same problem. All are migrated
and `test/core/design/color_conformance_test.dart` now bans the read.

**The ban is not zero-allowlist, unlike the icon ban, and the difference is structural.**
`icons.dart` may be the only file naming an `IconData`, so that ban can be absolute. Colors
have a **definition layer**: a pack seeds its roles from constants and a preference provider
falls back to one, so an absolute ban outside `colors.dart` would forbid the mechanism from
existing. The allowlist admits only files that *define what a role resolves to* — never one
that *paints* with it, which a widget always does — and a second test asserts each entry still
reads `AppColors`, so an exemption cannot outlive its reason. One entry is there for a
different reason than the rest: `categories_service.dart`'s presets are **persisted user
data**, and re-pointing them at the theme would make categories a user already saved drift when
a pack changes.

**Counting call sites understates this class of defect, because the worst bypasses never spell
the constant.** Two were found only by migrating: `LearningState` and `ReviewRating` each
carried a baked `Color` field, so a widget reading `state.color` skipped the theme without
naming `AppColors` at all — invisible to the very gate meant to catch it (the field is now
deleted; the lookup is `AppSemanticTheme.colorForState` / `colorForRating`). And a Riverpod
`FutureProvider` in `calendar_view.dart` built rows carrying a resolved `Color`, deciding a
pixel from a layer with no `BuildContext` (it now carries a *kind*; the widget resolves).
**A domain enum or a provider holding a `Color` is the same defect as a raw constant, and it
is harder to see.**

**`AppMediaChrome` — for surfaces that are dark on purpose.** Video player, trim timeline and
instax viewer named `AppColors.darkBg`/`darkCard`/`darkFill` because they must stay dark under
a bright photo regardless of app brightness. The *intent* is legitimate, which is exactly why
those constants survived every prior review. The `ThemeExtension` resolves the **active pack at
`Brightness.dark`**: intent preserved, pixels returned to the theme, and a pack now owns its
media chrome. Read it with `AppMediaChrome.of(context)`; never re-introduce a `dark*` constant
for this.

**A `CustomPainter` has no `BuildContext` — resolve in `build`, pass the value down.** Four
painters and three top-level helpers were the migration's hard cases. Doing it correctly made
`_FlowGraphPainter` *smaller*: passing the resolved ink deleted three
`brightness == Brightness.light ? AppColors.lightText : AppColors.darkText` ternaries, because
the theme already answers that question and duplicating it was precisely what kept the canvas
outside the pack and the overlay.

## Gotchas

- **`AppMotion` lives in `spacing.dart`, not a `motion.dart`.** There is no `motion.dart`.
  Grepping for the motion tokens by filename misses; grep the symbol `AppMotion`. It is
  co-located with `AppSpacing`/`AppRadius` for historical reasons.
- **`springGentle`/`springBouncy`/`morph` are `static final`, not `const`.** They construct a
  `_SpringCurve` (which builds a `SpringSimulation`) at first access, so they cannot be
  `const`. Everything else in `AppMotion` is `const`. Do not "fix" them to `const`.
- **The static `AppTypography` getters are Inter-locked.** They hardcode `'Inter'` and ignore
  the user's `AppFontFamily`. Only `AppTypography.textTheme(...)` (what `AppTheme` feeds
  Material) honors the selection. A widget reaching for `AppTypography.titleLarge` directly
  renders Inter regardless of the user's font preference — usually correct, occasionally a bug.
- **The CSS column is a promise.** `tokens.css` does not exist yet; treat any web-side token
  claim as unverified until the file lands and is checked against the Dart constants.
- **`AppColors` is pack data, not the vocabulary.** Reaching for `AppColors.accent` in a widget
  compiles and renders — and bypasses both the pack and the accessibility overlay. Read color
  from `Theme.of(context)` / `AppSemanticTheme.of(context)`. The 241 existing violations are a
  tracked migration (2.5), not precedent.
- **`ColorScheme.error` is overlay-owned, and `onError` is *measured*, not inherited.** `error`
  was hardwired to the `actionAgain` value in every mode and followed no overlay (fixed by
  `add-color-packs` 2.4). A pack still seeds it under `standard` — `error` and `actionAgain` are
  distinct meanings — but under any overlay the overlay's value wins, like every other `signal`.
  The trap is the ink: white reads **3.9:1** on Okabe–Ito vermillion in light mode, so
  `AppTheme._legibleInkOn` re-picks between the reading ink and the background by
  `contrastRatio` rather than defaulting to white. Do not "simplify" that back to
  `Colors.white`; the gate in `accessible_palette_test.dart` covers every palette × brightness.
- **`oklch.dart` needs a *signed* cube root.** A round trip drives the LMS terms negative, where
  `pow` returns NaN. Do not "simplify" `_cbrt` to `pow(x, 1/3)`.
- **Shadows and depth are functions, not constants.** `AppShadows.soft(brightness)` and the
  `AppDepth` levels vary by brightness/elevation and inline their own `Color(0x…)` shadow
  alphas — these ARGB shadow colors are *not* on the grid and are not `AppColors` tokens; do
  not flag them as color-token violations.

## Standards this chapter enforces

- No raw `Curve`/`Duration` literal drives visible motion on a product surface; use an
  `AppMotion` token and let the alias name its family (Fluid or Morph).
  ([`#motion-1`](./09-standards.mdx#motion-1))
- Overshoot curves (`expressive`, `springBouncy`) require a justified call-site comment; they
  are outside the two families. ([`#motion-2`](./09-standards.mdx#motion-2))
- Every visible transition is classifiable as **Fluid** (opacity/translation, default) or
  **Morph** (one element's shape/layout continuity); nothing else is a transition.
  ([`#motion-3`](./09-standards.mdx#motion-3))
- A spatial or radius literal equal to a token value resolves to the named token; off-scale
  values are justified, not silently inlined. ([`#grid-1`](./09-standards.mdx#grid-1),
  [`#token-1`](./09-standards.mdx#token-1))
- Product text uses the `AppTypography` scale (Inter default); ad-hoc `TextStyle`
  sizes/weights that duplicate a scale step are violations. ([`#type-1`](./09-standards.mdx#type-1))
- Color never carries meaning alone — pair it with icon/shape/label on every semantic signal.
  ([`#token-2`](./09-standards.mdx#token-2))
