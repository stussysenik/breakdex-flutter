# Executor Onboarding

This chapter is for a fresh session — the student executor — about to touch this repo. It
defines the session-start protocol and the boundary of what you may change without escalating.
The rest of the manual tells you *how the code works*; this tells you *how to work here*.

## Primitives

**The NOW block.** The single source of "what to do next." Root `ROADMAP.md` has a `## NOW`
section naming the ONE active change and its next unticked task. It exists so you never re-derive
priorities from the 30+ open changes. The NOW block is authoritative over your judgement about
what "seems important."

**A change.** An `openspec/changes/<id>/` directory: `proposal.md` (why/what), optional
`design.md` (rulings), `tasks.md` (the ordered checklist), and `specs/` deltas. Non-trivial work
is driven through a change ([`openspec/AGENTS.md`](../../openspec/AGENTS.md)).

**The same-commit ledger.** Work and its `tasks.md` checkbox land in one commit
([`#ledger-1`](./09-standards.mdx#ledger-1)). A pending change whose tasks contradict shipped
code is a review violation to reconcile before building on it.

**Teacher vs. student.** The teacher owns sequencing, scope, and the locked stack; the student
executes the next task exactly. This split only works because the manual lets the student locate
every seam without archaeology — which is why the manual exists.

**A crew, when there is one.** Root `CLAUDE.md` → **Crew protocol** splits any one lane across
three agents: **A** architect (plan, ledger, conflict rulings), **B** executor (code + the tests
that prove it), **C** auditor (the gate report, stated as what is and is *not* proven). It does
not add a fourth session type — a crew is still one lane, and A/B/C never mix Scholar with
Student any more than a solo session may. Two rules matter more than the roster: **B and C never
talk to each other** (A is the hub, and A decides when they disagree), and **every finding lands
in `tasks.md`** — a handoff that exists only in a conversation did not happen, which is the same
reason the `session.log` line is non-negotiable below. The per-handoff token caps are a
decomposition instrument, not a budget: a task whose assignment does not fit on a screen is the
wrong size, and the fix is at the spec level, not the implementation's.

## The session-start protocol

Do this before anything else, every session:

1. **Read `ROADMAP.md` → `## NOW`.** It names the active change and the next unticked task. That
   is your work. Do not pick a different task because it looks easier or more interesting.
2. **Open that change's `tasks.md`.** Execute exactly the next unticked task, per
   `openspec/AGENTS.md` (binary truth, ledger rule).
3. **Tick the box AND advance `## NOW`** in the *same commit* that lands the work
   ([`#ledger-1`](./09-standards.mdx#ledger-1)).
4. **If the task is owner-gated, stop and surface it** — then work only the parallel-allowed
   track the NOW block names, nothing else.
   <br/>**The same applies to a lane mismatch, which is easier to miss.** The next unticked task
   may belong to a *different session type* — a change's disposition table can mark an item
   Scholar or Teacher (`6.6` and `6.8` in `redesign-visual-first-experience` both are). An
   Executor cannot open one: the deliverable is a spec, not code, and improvising the missing
   decision in the implementation is exactly the bias the three lanes exist to prevent. Say so,
   pick up the nearest *implementable* open task, and record the reroute — do not silently
   implement a Teacher task, and do not stall with nothing delivered.
5. **Append one line to `docs/manual/session.log`**:
   `YYYY-MM-DDThh:mm+TZ <role> <change-name> <what happened>`, including what is *not* proven.

Grounding for the task's subject matter comes from this manual: the chapter whose `watches` cover
the files you're touching is your reference. If your change alters a documented seam, update that
chapter's body and `verified:` frontmatter in the same commit
([`#ledger-2`](./09-standards.mdx#ledger-2)).

**The `verified:` stamp lags the work by exactly one commit, and that is not a bug.**
`scripts/docs_ledger_check` diffs `verified..HEAD` over the chapter's `watches`, so a chapter
cannot name the commit that is still being written. Land the work (body edits included), then
set `verified:` to that commit's hash in a follow-up commit which touches no watched path. A
stamp pointing at a commit that does not exist is worse than a stale one: `git diff` aborts, and
the gate reports `Command failed` instead of drift — it stops being able to see anything at all
(the `fcc65bd` incident, `redesign-visual-first-experience` 6.12). Never invent a hash, and never
re-stamp without re-reading the chapter — the gate compares commits, not meaning, so a false
stamp is a lie it cannot catch.

## Close the session in the record, not the transcript

Root `CLAUDE.md` → **Context budget** governs the landing. Budget the session so the last stretch
writes findings down; a session that runs out mid-task loses everything it learned and did not
record. The final three actions are non-negotiable and happen even when the budget is gone: the
ledger tick, the `## NOW` advance, and the `session.log` line. A **ruled-out hypothesis is a
finding** — record what you proved false and how, so the next session does not re-run the
experiment. Report against what was *asked*, listing each item done or not done; a summary that
narrates only completed work hides the gap it exists to surface.

## What a student may and may not touch

**Freely, within the current task:**

- Implement the next unticked task's code, additively, matching surrounding style
  ([`#diff-1`](./09-standards.mdx#diff-1), [`#diff-2`](./09-standards.mdx#diff-2)).
- Write and run tests; verify on the iOS-sim target ([`#test-3`](./09-standards.mdx#test-3)).
- Update the manual chapter for a seam you changed, and tick your `tasks.md` boxes.

**Only with teacher/owner escalation — stop and surface, do not proceed:**

- **Reordering the queue** or starting a different change. Only the owner reorders.
- **Touching the locked stack** (root `CLAUDE.md` "Canonical stack — LOCKED": Appwrite backend,
  Drift canonical, `Machine<S,E>`, XState-v5 web mirror, token source, layout doctrine, motion
  doctrine, the icon system, and the color system). These are decided; re-litigating one is a
  teacher decision. Three of those rows are enforced by a **conformance test** rather than by
  review — the frame, `icon_conformance_test.dart`, and `color_conformance_test.dart` — so
  breaking them is a red suite, not an argument. The review-checklist wording for each lives in
  `openspec/AGENTS.md`, and the two icon/color bans are deliberately different shapes: the icon
  ban is absolute, the color ban admits a named definition layer. Copying one onto the other is
  a mistake, not a simplification.
- **Building a non-goal** (E2EE, CRDTs, Temporal, shared/collaborative state). If a task seems to
  require one, that is the signal to escalate ([Product Doctrine](./01-product-doctrine.mdx)).
- **Acting on a superseded spec.** A queued change is not automatically live. If a task
  contradicts the locked stack, escalate rather than build it — and see the
  [Supersession rule](../../CLAUDE.md) plus
  `openspec/changes/archive/2026-07-29-ARCHIVE-NOTE.md`, which retired six changes proposing a
  Phoenix/BEAM/Gleam backend, protobuf transport, and CRDTs. They sat in the active queue for
  89 days after the Appwrite ruling killed them. Age in the queue is not evidence of relevance.
- **Destructive data operations** — deleting/orphaning user state, non-additive migrations. The
  repo is late-stage production ([`#brownfield-1`](./09-standards.mdx#brownfield-1),
  [`#brownfield-2`](./09-standards.mdx#brownfield-2)).

## Do not re-triage the queue

`CLAUDE.md` → **Queue doctrine** already decided it. In short: work the `## NOW` block and
stop reading the board. `INVALID` blocks archiving, not implementing — repair it only when
that change becomes active. A triage decision goes in the change's `.triage` file
(`reviewed: YYYY-MM-DD` or `exempt`) so it is never re-asked. Tasks needing a device, owner
credentials, or a console belong to `owner-verification-passes`, never to a parent change.

## The two web surfaces are ranked, not equal

Re-affirmed 2026-07-29. Confusing these is the most common orientation error:

- **Flutter Web is the product** — the released consumer app, same codebase as mobile. When
  the surfaces compete for effort or diverge in behavior, Flutter wins by default.
- **`web-mirror/` (Next.js + XState) is an owner-only dev utility** — a privileged test
  harness and authoring studio. It is deliberately allowed to reach data and force states the
  consumer app cannot; that privilege is why it is kept. It is a tool for building the
  product, never a second product. Never ship a user-facing feature there first.

A corollary for verification: exercising Flutter Web proves shared Dart logic, UI, and state
machines for all targets, but **not** storage (WASM/OPFS vs native SQLite), video (HTML
`<video>` vs native player), Photos/permissions, secure storage, or plugin paths — web
short-circuits several native paths with `if (kIsWeb) return;`. Web-green is not mobile-green.

## Reasoning from the primitives

- **You cannot be lost about priorities.** There is exactly one NOW block; if it and your
  instinct disagree, the NOW block wins or you escalate.
- **You cannot silently drift the ledger.** Because ticking rides the work commit, a reviewer can
  trust that a ticked box means shipped code — and an unticked-but-shipped state is itself the
  bug to fix ([`#ledger-1`](./09-standards.mdx#ledger-1)).
- **You cannot quietly expand scope.** Anything outside the current task's files is either a
  surgical necessity you name, or an escalation — never a drive-by.
