# Data Layer

Drift (a typed SQLite wrapper) is the **canonical on-device source of truth** for every domain entity in Breakdex. The backend is a shadow copy — reconciled per-entity, never authoritative until verified ([Sync](./04-sync.mdx)). Everything a screen renders, and every mutation the app persists, passes through the primitives defined here. Source: `lib/core/database/` (hand-written schema + DAOs) and `lib/core/data/` (repositories). The generated file `database.g.dart` is derived output — read it only to confirm a data-class or companion name, never to author schema.

This chapter defines the primitives, then reasons up: the layering, the migration discipline, and the FSRS gotchas all follow from a small set of definitions.

## Primitives

**Table.** A hand-written `class X extends Table` under `lib/core/database/tables/` whose getters declare columns (`TextColumn get id => text()()`). The table class is the *schema*; it is never instantiated. Its `primaryKey` getter names the key columns. Example — `Moves` (`tables/moves.dart`) declares `id` (PK), `name` (`withLength(min: 1)`), `videoPath` (nullable), `updatedAt` (nullable, the LWW clock), `deletedAt` (nullable, the inbound-tombstone soft-hide — distinct from user `archivedAt`), and `createdAt`.

**Data class.** The immutable row value Drift generates from a `Table`: `class Move extends DataClass`, `class Combo`, `class Review`, `class FsrsCard`, `class BreakdexSet`, `class SetItem`, `class ComboMove`, and so on (see `database.g.dart`). One row = one `const`-constructible value object. Reads return these; the UI renders these. Note the naming skew: the `Sets` table produces **`BreakdexSet`** (not `Set`, which is a Dart core type), and `SyncLog` produces `SyncLogData`.

**Companion.** The generated *partial-update* value: `MovesCompanion`, `FsrsCardsCompanion`, `ReviewsCompanion`. Every field is wrapped in `Value<T>` so "absent" (`Value.absent()`, i.e. `.present == false`) is distinct from "explicitly null" (`Value(null)`). Writes take companions; a field you omit is a field you don't touch. This absent/null distinction is load-bearing across the codebase (e.g. the LWW timestamp stamp, below).

**DAO.** A `class XDao extends DatabaseAccessor<AppDatabase> with _$XDaoMixin`, annotated `@DriftAccessor(tables: [...])`, with `part 'x_dao.g.dart'`. It owns the queries for its tables — `select`, `into().insert`, `update().write`, `.watch()` streams. DAOs are the *only* layer that speaks SQL. Example: `MovesDao` (`daos/moves_dao.dart`) exposes `watchAll()`, `insertMove`, `archiveMove`, etc.

**Schema version.** The single integer `AppDatabase.schemaVersion` (`database.dart`). **Currently `27`.** It is the monotonic counter that drives migrations: bump it by one for every schema change and add a matching `if (from < N)` block.

**Migration.** The `MigrationStrategy` on `AppDatabase`: an `onCreate` (fresh install → `createAll()` + triggers) and an `onUpgrade(m, from, to)` that runs each `if (from < N)` block in order to walk a legacy DB forward to the current schema.

**Polymorphic key.** A `(entityId, entityType)` composite that lets one table serve multiple entity kinds without a foreign key to either. `FsrsCards` uses it as its literal `primaryKey`; `ReviewableItem` is its typed reflection in Dart.

## Reasoning from the primitives

Four properties follow directly:

1. **Reads are streams; the UI is reactive by construction.** DAO query methods return `Stream<List<T>>` via Drift's `.watch()`. Any write to a watched table re-emits — so `UI = f(rows)` with no manual invalidation. A method that returns `Future` instead of `Stream` is a one-shot snapshot and will *not* re-emit (the documented `Future.asStream()` anti-pattern lives outside this layer).

2. **Partial updates are total over intent.** Because a `Companion` distinguishes absent from null, `updateMove` can express "rename this move, touch nothing else" and "clear this move's `archivedAt`" as two different companions. No update needs a full row.

3. **Migrations are forward-only and idempotent.** Each `if (from < N)` block is additive and guarded so it survives being re-run against a legacy DB that partially matches the current definition. This is a brownfield invariant, not a nicety (real users, real data on disk).

4. **Polymorphism is a convention, not a constraint.** `(entityId, entityType)` carries no DB-enforced FK, so a card can outlive its entity (an *orphan*). The read path must tolerate that — and it does, via `LEFT JOIN` + `readTableOrNull`.

## Schema, tables, and the migration ladder

`AppDatabase` (`database.dart`) is annotated `@DriftDatabase(tables: [...26 tables...], daos: [...18 DAOs...])`. The canonical ERD — moves↔fsrs_cards (1:1), moves↔reviews (1:N), combos↔combo_moves, sync_log tracking — lives in **[`../architecture.md`](../architecture.md)** and is not redrawn here. Read it for the entity graph; read this for the mechanics. (Note: that ERD's FSRS PK label and backend node are stale versus the live schema — see the index note below; a good first drift-check work order.)

The migration ladder is the schema's history, each rung an `if (from < N)`:

```dart
@override
int get schemaVersion => 27;

onUpgrade: (m, from, to) async {
  if (from < 5)  await m.addColumn(moves, moves.originalVideoName);
  if (from < 8)  { /* fsrs_cards: moveId PK → (entityId, entityType) composite PK */ }
  if (from < 10) { /* asset sync engine tables */ }
  if (from < 22) { /* combo journey; PRAGMA-guarded ADD COLUMN */ }
  if (from < 23) {
    // additive + backfilled: SQLite forbids ADD COLUMN with a non-constant default
    await customStatement('ALTER TABLE moves ADD COLUMN updated_at INTEGER');
    await customStatement('UPDATE moves SET updated_at = created_at WHERE updated_at IS NULL');
  }
  if (from < 24) { /* combos.updated_at + combo_moves.updated_at LWW clocks (4.4) */ }
  if (from < 25) { /* deck_moves.updated_at LWW clock (4.7) */ }
  if (from < 26) { /* deleted_at soft-hide on moves/combos/combo_moves/decks/deck_moves (4.8) */ }
  if (from < 27) { /* note-entry updated_at + deleted_at (4.9) */ }
  await _backfillReviewSnapshots();
  await _installIntegrityTriggers();  // re-run every upgrade — triggers are IF NOT EXISTS
}
```

The v24–v27 rungs are the Appwrite strangler-fig spreading the two sync columns across the synced tables, and they follow the same disciplines: `updated_at` is added nullable then backfilled (from the row's own `created_at`, or — for join tables with no `created_at`, like `combo_moves`/`deck_moves` — from the parent's clock); `deleted_at` is added nullable with **no** backfill (NULL = "not deleted" is already correct for every existing row). `deleted_at` is the *inbound tombstone soft-hide* (v26): a delete on device A reaches device B as a tombstone that stamps `deleted_at` instead of hard-deleting, so a remote delete never destroys rows or videos — a local delete still hard-deletes on its origin device. Every browse/list read filters `deleted_at IS NULL` (in `MovesDao` the `_isActive`/`_isArchived` predicates both require it — a remote-deleted row is neither active nor archived); for left-joins the step-level predicate rides the ON clause so a combo whose only steps are hidden still lists.

Three disciplines are visible in the source and are mandatory for any new rung:

- **Non-constant defaults are illegal in `ADD COLUMN`.** SQLite rejects `ADD COLUMN … DEFAULT (strftime(...))`. The v23 and v22 blocks add the column *nullable* (or `DEFAULT 0`), then backfill with a second `UPDATE`. Never inline a dynamic default.
- **Guard against legacy drift with `PRAGMA table_info`.** `_columnNames(table)` reads the live columns so a block can skip an `ALTER` a legacy device already applied (the v22 `combos.status` / `created_at` adds). An upgrader from an old version may already carry columns the current definition includes.
- **Triggers and backfills re-run on every upgrade.** `_installIntegrityTriggers()` (case-insensitive unique-name enforcement across `moves`/`combos`/`sets`, and dedup on `combo_moves`/`set_items`) uses `CREATE TRIGGER IF NOT EXISTS`, so it is safe to call at the tail of both `onCreate` and `onUpgrade`. The uniqueness rule that a move, combo, and set cannot share a name is enforced *in SQL*, not just in Dart.

The v8 rung is the canonical polymorphic migration: it renamed the old `fsrs_cards` (single `moveId` PK, FK to moves) to `_old`, created the new table with `PRIMARY KEY (entity_id, entity_type)` and **no FK** (a polymorphic ref can't FK to two tables), copied every legacy row in as `entity_type = 'move'`, and dropped `_old`.

## DAOs and the codegen step

A DAO declares its tables and defers its generated mixin to a `part` file:

```dart
part 'fsrs_cards_dao.g.dart';

@DriftAccessor(tables: [FsrsCards, Moves, Combos])
class FsrsCardsDao extends DatabaseAccessor<AppDatabase> with _$FsrsCardsDaoMixin {
  FsrsCardsDao(super.db);
  // select(fsrsCards), into(fsrsCards).insertOnConflictUpdate(...), etc.
}
```

The `_$FsrsCardsDaoMixin`, the `Move`/`FsrsCard` data classes, the `MovesCompanion`, and the `$MovesTable` accessor are all **generated**. After editing any table or DAO you MUST regenerate:

```
dart run build_runner build --delete-conflicting-outputs
```

Skipping this leaves the hand-written schema and `database.g.dart` out of sync — the analyzer will flag missing symbols, and a stale `.g.dart` is a build-breaking, not a runtime, failure.

DAO idioms worth matching: reactive reads use `.watch()`/`.watchSingle()`; a JOIN result is packed into a hand-written value class (`FsrsCardWithEntity`) via `readTable`/`readTableOrNull`; an upsert on a composite PK is `insertOnConflictUpdate`. `MovesDao._stampUpdatedAt` shows the companion-presence idiom in action — it stamps `updatedAt` with `DateTime.now().toUtc()` **only if the caller left it absent**, so the reconcile path can pass a remote timestamp that must be preserved rather than clobbered. That idiom is now a family: `CombosDao._stampCombo`/`_stampComboMove`, and the decks/note-entry DAOs' equivalents, apply the same absent-only stamp on every insert/update of a synced table.

## The three-layer repository

Every domain entity is reached through three composed layers, defined across `lib/core/data/`. The layering is a decorator stack, not an inheritance chain:

| Layer | File | Role |
| --- | --- | --- |
| **Abstract** | `repositories.dart` | The interface — `MoveRepository`, `ComboRepository`, `ReviewRepository`, `SetRepository`. Pure Dart contract; names the reads and writes, knows nothing of Drift. |
| **DriftRepo** | `drift_repositories.dart` | `DriftMoveRepository implements MoveRepository`. A thin adapter that forwards each method to the DAO. This is the only layer that holds a DAO. |
| **SyncAwareRepo** | `sync_aware_repositories.dart` | `SyncAwareMoveRepository implements MoveRepository`. A **decorator** wrapping an inner `MoveRepository` (the DriftRepo) plus a `SyncDao` and optional `ProvenanceService`. |

The decorator is the reason writes and reads are treated asymmetrically:

```dart
// Reads — zero overhead, delegate directly
Stream<List<Move>> watchAll() => _inner.watchAll();

// Writes — delegate, then log the mutation for sync + provenance
Future<void> insert(MovesCompanion move) async {
  await _inner.insert(move);
  await _syncDao.logChange(entityId: move.id.value, table: 'moves',
                           action: 'create', hasVideo: /* … */);
  await _provenance?.logCreated('move', move.id.value, metadata: {'name': move.name.value});
}
```

Reads pass straight through (the decorator adds nothing). Writes go `inner → _syncDao.logChange → _provenance`. That `logChange` row is what the sync layer later drains ([Sync](./04-sync.mdx)); the abstract interface exists so a screen depends on `MoveRepository`, never on whether sync is wired. Because the interface is identical at every layer, the stack is assembled by wrapping, and a test can inject a bare DriftRepo with no sync side effects.

## FSRS integration and its gotchas

FSRS (Free Spaced Repetition Scheduler, `fsrs: ^2.0.1`) schedules review. The `fsrs_cards` table is the persisted state; `FsrsService` (`lib/core/services/fsrs_service.dart`) is the bridge to the package. Three impedance mismatches make this the sharpest corner of the data layer.

**1. State enum has a `+1` offset — there is no package state `0`.** The `fsrs.State` enum starts at `learning = 1` (then `review = 2`, `relearning = 3`); the package has **no zero**. The DB, however, uses `fsrsState = 0` as a *custom "New / never reviewed"* convention. The bridge reconciles this explicitly in `_dbToFsrs`:

```dart
fsrs.Card _dbToFsrs(FsrsCard dbCard) {
  if (dbCard.fsrsState == 0) {                    // our "New" — no package equivalent
    return fsrs.Card(cardId: dbCard.entityId.hashCode,
                     state: fsrs.State.learning, step: 0, due: dbCard.due.toUtc());
  }
  return fsrs.Card(
    cardId: dbCard.entityId.hashCode,
    state: fsrs.State.fromValue(dbCard.fsrsState),          // 1|2|3 → enum
    step: (dbCard.fsrsState == 1 || dbCard.fsrsState == 3) ? 0 : null,
    stability: dbCard.stability > 0 ? dbCard.stability : null,   // 0.0 → null
    difficulty: dbCard.difficulty > 0 ? dbCard.difficulty : null,
    due: dbCard.due.toUtc(), lastReview: dbCard.lastReview?.toUtc());
}
```

Any code switching on `fsrsState` must group `1 || 3` (learning + relearning) and treat `2` as mastered — as `learningStateFromFsrsState` and `getDueSummary` both do. Writing back, `postState = updated.state.value` re-encodes the enum to its int.

**2. Package `Card` is constructed, not deserialized; the DB is the store of record.** `FsrsService` builds `fsrs.Card(...)` directly from DB columns — it does **not** round-trip through `Card.fromMap`. `cardId` is synthesized as `entityId.hashCode` (the package needs an int id; ours are text). The package `Card` tracks neither `reps` nor `lapses`, so the service maintains those itself (`newReps`, `newLapses` in `processReview`) and persists them to our columns. The package object is transient scheduling scratch space; the `FsrsCardsCompanion` upsert is the durable truth.

**3. UTC discipline is absolute.** Every timestamp entering or leaving the scheduler is coerced: `.toUtc()` on `due`/`lastReview` in `_dbToFsrs`, and time reads go through `AppClock.nowUtc()` (`lib/core/utils/app_clock.dart`) — an injectable clock whose only production impl returns `DateTime.now().toUtc()`. A naive local `DateTime` mixed into scheduling math produces wrong intervals across timezones. Persisted or cross-device-compared timestamps use the clock; never `DateTime.now()` bare.

## The polymorphic reviewable wrapper

`ReviewableItem` (`lib/core/models/reviewable_item.dart`) is the typed face of the `(entityId, entityType)` key — a `sealed class` with exactly two subtypes, `ReviewableMove` and `ReviewableCombo`, each surfacing a uniform `entityId` / `entityType` / `displayName` / `category` / `videoPath`:

```dart
sealed class ReviewableItem {
  String get entityId;   String get entityType;
  String get displayName; String? get category; String? get videoPath;
}
class ReviewableMove  extends ReviewableItem { /* entityType => 'move'  */ }
class ReviewableCombo extends ReviewableItem { /* entityType => 'combo', category => null */ }
```

Because it is `sealed`, a `switch` over it is exhaustively checked by the compiler — the review UI branches on move-vs-combo with no runtime type test. The DAO-level JOIN (`FsrsCardsDao.getDueCardsWithEntities`) `LEFT JOIN`s `moves` and `combos` on `entityId` gated by `entityType`, then `ReviewableItemWithCard.fromEntity` maps the result: if neither side resolved (an orphan card whose entity was deleted), it fabricates a placeholder `Move(name: 'Unknown')` rather than crashing. This is property 4 above made concrete — the missing FK is tolerated by the read path, not forbidden by the schema.

## Standards this chapter enforces

- Every schema change bumps `schemaVersion` by one and adds a matching `if (from < N)` block; migrations are forward-only. ([`#data-1`](./09-standards.mdx#data-1))
- `ADD COLUMN` never uses a non-constant default — add nullable, then backfill with `UPDATE`; guard legacy adds with `_columnNames`/`PRAGMA`. ([`#data-2`](./09-standards.mdx#data-2))
- Run `dart run build_runner build` after any table/DAO edit; a stale `.g.dart` is a build failure. ([`#data-3`](./09-standards.mdx#data-3))
- SQL lives only in DAOs; screens depend on the abstract repository interface, never on Drift or the DAO. ([`#data-4`](./09-standards.mdx#data-4))
- Reactive reads return `.watch()` streams; never surface a `Future` snapshot where the UI must re-render on change. ([`#data-5`](./09-standards.mdx#data-5))
- All persisted/compared timestamps go through `AppClock.nowUtc()` / `.toUtc()`; the FSRS state offset (`0 = New`, package `learning = 1`) is honored on both encode and decode. ([`#data-6`](./09-standards.mdx#data-6))
