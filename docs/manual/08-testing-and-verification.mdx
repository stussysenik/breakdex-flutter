# Testing & Verification

Verification in this repo is governed by one axiom from root `CLAUDE.md` §9 — **Binary Truth** — and the honest fact that the automated gate enforces only a slice of it. This chapter defines the verification primitives, then reasons up from them: what counts as proof, where proof can actually be produced, and which failures are proof of nothing.

## Primitives

**Binary truth (confidence 0/1).** A claim about the code is either terminally proven or it is unproven — there is no 0.8. "It compiles," "the analyzer is clean," "the request returned 200" are all *0*: they are necessary, not sufficient. Proof is a terminal-observed result — a green test, a rendered DOM node, a screenshot, a log free of the error class in question. No success claim ships without it (root `CLAUDE.md` §9).

**Terminal-verified proof.** The observable output of *running the thing*: an `exit 0` from the relevant test, `flutter analyze` reporting `No issues found`, or a boot log line that proves a runtime invariant. Proof is a captured artifact you can point at, not an inference from "the diff looks right."

**Runtime verification target.** The one execution environment where a change can actually be *seen* running. This repo has exactly one reliable local target — the iOS simulator. The two "quick" targets (macOS desktop, Chrome/web) do not boot for reasons unrelated to any given change (below). Naming the target is load-bearing: a claim of "verified at runtime" is only meaningful against a target that boots.

**Red/green discipline.** The proof protocol for a bug fix: a failing repro *first* (`exit 1`), then the smallest precise fix, then the *same* repro green (`exit 0`). The red run proves the test can fail — i.e. that it tests the bug — before the green run proves the fix. A green-only test proves nothing about the bug it claims to cover.

From these four, everything below is forced: the CI gate is a *floor* (it proves cheap things cheaply), runtime proof requires the named target, and any test result that is neither red-then-green nor a known-baseline failure is not yet proof.

**Conformance tests are a distinct category**, and they do not all live in `test/design/` —
the category is defined by what it asserts, not by where it sits. Two shapes are in use:

- **Source-level.** `test/design/frame_conformance_test.dart` reads screen *source* and fails
  if a screen on the roster builds its own `Scaffold`/`AppBar`/`SliverAppBar`. Since 2026-08-01
  it is **closed rather than enumerated**, and that is the more useful shape to copy: four
  tables partition every chrome-building file under `lib/` — `_onFrame`, `_frameless` (no bands
  at all, on purpose, and never an `AppBar`), `_awaitingRuling` (**empty since 2026-08-01**; it
  is kept as the place a decision owed gets written down), `_framework` — and a closure test
  walks `lib/` and fails on any
  such file in **no** table. An allowlist can only assert about files it already knows; a
  closed table fails on the commit that adds an unlisted one. The cost is that every exemption
  must be *written*, which is the point: `flashcard_review_screen`'s immersive drill session
  and the pre-auth login door are frameless with their reasons in the table, and the bound on
  frameless is the same for both — a surface with no bands may own a `Scaffold` and may never
  own an `AppBar`.
  `test/design/type_baseline_test.dart` is the same shape for the type scale.
  `test/core/design/icon_conformance_test.dart` and `color_conformance_test.dart` ban raw
  `Icons.*` and raw `AppColors.*` respectively, and `test/design/morph_conformance_test.dart`
  bans a raw `Hero(` outside `AppMorph` — a shared element that skips the seam rides the route's
  linear animation instead of `AppMotion.morph`, which is the Fluid feel applied to a Morph
  problem. **The two bans are deliberately not the same
  shape, and copying one onto the other is a mistake**: the icon ban is absolute
  (zero-allowlist, since exactly one file may name an `IconData`), while the color ban admits a
  named **definition layer**, because a pack must seed its roles from constants and a
  preference provider must fall back to one — an absolute color ban would forbid the mechanism
  from existing. A source-level ban is also **only a spelling check**: it cannot see a domain
  enum or a provider that holds a resolved `Color`, which is why the color pass pairs it with
  `color_migration_test.dart` (below).
- **Structure-level.** `test/core/navigation/settings_section_transition_test.dart` walks the
  live `appRouter` and fails any `/settings-panel*` route declared without a `pageBuilder`,
  so a new settings section cannot ship with the default push transition by accident. It
  asserts over a built object graph rather than over text, which is the sturdier form when
  the invariant has a runtime representation to walk.

A third shape appeared with the color work: **the test that red-proves a design decision.**
`test/core/design/oklch_test.dart` does not only check that the conversion is correct — it
asserts the *comparison* the decision rests on. OKLCH was chosen over HSL because equal HSL
lightness is not equal perceived lightness, so the suite builds both ramps and measures the
gap: HSL spreads yellow against blue by more than 0.3 of the visible lightness range, OKLCH by
less than 0.01. Reach for this shape when a design document contains a claim about the physical
world that the implementation depends on. The alternative is a paragraph nobody can falsify,
and the cost of being wrong is ~140 lines of arithmetic nobody needed.

A **property gate** is the same instinct applied to a whole matrix rather than one claim:
`accessible_palette_test.dart` asserts WCAG contrast over every colour pack × both brightnesses
× the pairs that actually render, so a new pack cannot ship unreadable without failing CI. The
discipline that makes it usable is choosing pairs that correspond to real pixels — a matrix over
every role against every other role would be larger, mostly meaningless, and would have to be
weakened until it passed.

A fifth shape closes the color work: **the test that asserts the pre-fix value fails.** A
conformance ban proves nobody *spells* the banned name; it cannot prove the migrated call sites
now render what the theme says. `test/core/design/color_migration_test.dart` reads the migrated
helpers under `AccessiblePalette.deuteranopia` and asserts they return Okabe–Ito `#009E73`, not
the classic `#1F8A70` they were pinned to — and that claim was **run red**: restoring the
constant at one `statusStyle` case turns two tests red, reverting the revert returns all seven
green. Pair a spelling gate with a behavioral one whenever the migration's whole point is a
behavior the spelling cannot see.

**A gotcha that cost a wrong diagnosis in that pass, and will cost you one too:** `MaterialApp`
wraps its child in an `AnimatedTheme`, so swapping `theme:` between pumps is **lerped**, and
`ThemeExtension.lerp` holds the *old* value for `t < 0.5`. A single `pump()` therefore reads
the **previous** theme. The first run of these tests reported the classic green under
deuteranopia and looked exactly like a failed migration; the migration was fine and the harness
was lying. Use `pumpAndSettle()` after any theme swap you intend to read.

A fourth shape sits beside it: **the test that pins a known defect on purpose.**
`color_packs_test.dart` asserts that grayscale modes still leak one red through
`ColorScheme.error`, and names the task that will turn it red. The alternative — leaving the
gap unasserted — loses it, and fixing it later looks like a regression to whoever runs the
suite. A test can encode "this is wrong and tracked" as legitimately as "this is right", as
long as the assertion says which.

It pays immediately, and not in the way intended: the OKLCH gamut fit shipped with a tolerance
of half an 8-bit step applied in *linear* RGB rather than encoded sRGB. The transfer function's
slope near black is 12.92, so a linear overshoot of 0.002 became six encoded code points and
the clamp rotated hue by 3.5° — breaking the fit's only guarantee. The measurement test caught
it; a "conversion round-trips" test would not have. The tolerances were then tightened to
values the broken code fails, which is the actual deliverable of a red/green pass.

The source- and structure-level shapes exist for the same reason: the layout constitution's
predecessor was a review rule, and review passed five screens that each grew a different header
([Design System](./05-design-system.mdx)). A rule with no failing gate is a preference. Reach
for this category when the invariant is about how code is *written or wired* rather than what
it computes — prefer walking a real graph over matching source text, and keep source matching
narrow, because a source test that over-matches becomes a refactor tax.

## What CI actually gates

`.github/workflows/ci.yml` — read it literally, do not assume it does more than it does:

```yaml
on:
  pull_request:
  push:
    branches-ignore: [main]      # CI runs on branches + PRs, never on main
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }        # full history — the docs ledger diffs verified..HEAD
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '3.41.3' }   # pinned exactly — '3.x' drifted to 3.44.6 and broke the web compile
      - run: flutter pub get
      - run: ./scripts/check_l10n.sh   # generated l10n must be committed + current
      - run: node scripts/docs_ledger_check   # manual chapters current with their watched code
      - run: flutter analyze
      - run: flutter build web         # the web release target must keep compiling (1.6 CI half)
```

Five gates: dependency resolution, **l10n freshness**, **docs-ledger freshness**, **static analysis**, and the **web compile** (a native-only import leaking past a platform seam fails here rather than in a browser — [Platform Seams](./07-platform-seams.mdx)).

- `scripts/check_l10n.sh` runs `flutter gen-l10n` and fails (`exit 1`) if `lib/l10n/gen` has any diff — i.e. the committed generated localizations must match the ARB sources ([Localization](./06-localization.mdx)).
- `scripts/docs_ledger_check` diffs each verified manual chapter's `verified..HEAD` restricted to its `watches` globs (git plumbing only) and fails if a watched path changed without the chapter being re-verified ([Manual Meta](./12-meta.mdx)). This is why `checkout` needs `fetch-depth: 0` — a shallow clone can't reach a chapter's `verified` commit.
- `flutter analyze` is the static gate. It must report `No issues found` — the `analysis_options.yaml` ruleset ([Standards](./09-standards.mdx)) is the real teeth here.

**CI does NOT run `flutter test`.** (It does now build one artifact — the web bundle — but only as a compile gate; nothing is published from CI.) The 198-file suite is *not* enforced on push or PR. This is a deliberately honest statement of the current floor: green CI proves the code analyzes and l10n is current — it does **not** prove the tests pass. Running `flutter test` before handoff is a manual discipline (§9), not something the machine does for you. Do not read a green CI check as "tests pass."

`release.yml` is separate: it fires only on `push` to `main`, runs `npx semantic-release` (Node 20, Flutter pinned `3.41.3`) for monotonic versioning + CHANGELOG, then a `detect` step checks for an exact-match tag on HEAD and — when a new version published — chains the `deploy-web` reusable workflow with that tag (done via `needs:` rather than `on: push: tags` because tags pushed by `GITHUB_TOKEN` don't trigger downstream workflows; the deploy self-skips when Vercel secrets are unset). It is a publishing pipeline, not a verification gate — it presumes the branch already earned its way to `main`.

> **The rule that resolves the ambiguity:** the CI check being green is a *floor* (analyze + l10n), never a ceiling. Terminal-verified proof for anything the analyzer can't see — behavior, rendering, migrations — is on you, produced locally against the runtime target, before you claim done.

## Runtime verification targets — iOS sim is canonical; web boots; macOS is dead

For any claim that requires *seeing the app run* (a screen renders, a flow completes, a migration applies), the target matters — one of the three obvious ones does not boot at all, and one is a compile/boot check rather than a full proof surface:

- **macOS desktop — dead end.** No `macos/` runner exists. `flutter run -d macos` → `"No macOS desktop project configured"`, exit 1.
- **Chrome / Flutter web — now compiles and boots.** The old dead end (a `sqlite3` FFI compile failure) was closed by the Phase 1.0 web foundation: the platform seams keep `dart:io`/`dart:ffi` out of the web graph, persistent web Drift is wired ([Platform Seams](./07-platform-seams.mdx)), `flutter build web` is a CI gate, and the app renders in Chrome with a clean boot console. Chrome is a legitimate compile/boot check; it is still *not* the canonical runtime-proof target for native or data-backed claims — browser-driven core-flow smoke (task 1.6) remains an open half.
- **iOS simulator — the working target.** Boot via `flowdeck` + `flutter run -d <udid>`; capture the accessibility tree + image with `flowdeck ui simulator screen --screenshot`.
- **Android emulator — scripted, not hand-driven.** `scripts/android_smoke.sh` is the gate: parse → boot → build → install → drive (Maestro) → exit code. It pins `Medium_Phone_API_35` (`ANDROID_AVD` overrides) and reuses an already-attached device, so the lab run and the owner's device run take the same path. `LINT_ONLY=1` stops after the device-free parse step, which returns in seconds — always run that first, because Maestro parses *every* flow under `.maestro/` before filtering by tag, so one stale flow in an unrelated tier blocks the whole smoke run. Tooling ruling: `openspec/changes/android-e2e/design.md` D1–D2 (Maestro is the Android driver; `argent` is iOS-sim/web only).

**Android is a distinct proof surface, and the cheap gates cannot see it.** On 2026-07-28 the analyzer, 1225 unit tests, and `flutter build web` were all green while the Android app was dead on launch — `DefaultFirebaseOptions.currentPlatform` threw before `runApp`, so it had never rendered a frame. Nothing short of running it on Android could have caught that. Treat "green suite" as a claim about the layers the suite covers, never about a platform nobody launched.

Practicals for the iOS-sim path (these are the difference between verifying and hanging):

- **First debug build is slow (~275s Xcode build).** `dart mcp launch_app` times out at 90s. Run `flutter run` in the background under a captured log and poll the log — do not sit on a foreground call that will time out.
- **Fresh sim = empty DB + no videos.** No moves/combos seeded, and the sim photo library shows `"NO VIDEOS FOUND"` in the picker, so you cannot reach move-detail by importing. To exercise data-backed screens, inject a video first (`simctl addmedia` / seed). Empty-state + chrome surfaces (nav, Review "Party" empty state, Add flow, picker) verify without seeding.
- **`App startup completed` in the boot log, with no `MissingResource`/`LocalizationsDelegate` hits, proves the whole l10n key set resolves** for the active locale — the delegate loads all keys eagerly, so a clean startup is a terminal proof of localization coverage ([Localization](./06-localization.mdx)).

## Red/green in practice

For a bug fix, the protocol is not "write a test that passes." It is:

1. **Red.** Write the repro as a `flutter_test` case that encodes the wrong behavior. Run it; confirm `exit 1`. If it passes on the unfixed code, it is not testing the bug — rewrite it.
2. **Fix.** The smallest precise change that the red test demands — no drive-by refactor (root `CLAUDE.md` §1).
3. **Green.** Re-run the *same* test unchanged; confirm `exit 0`.

The red step is the load-bearing one: it is the only thing that proves the test has teeth. This is the state-machine layer's natural mode — a `(state, event) → expected` row is a repro that either matches the transition table or does not.

Brownfield amplifies this: the repo is late-stage production with real user data ([Data Layer](./03-data-layer.mdx)). Changes are additive over invasive, migrations are one-way and must be tested, and a claim of done requires verification on a **real build**, not a passing unit test alone (root `CLAUDE.md`, brownfield row). A migration proven only by a green unit test is *not* proven — it is proven when the iOS-sim build boots against a populated DB without data loss.

## Never sleep for an async side effect — poll to a deadline

A fixed `await Future.delayed(...)` before asserting on an async result is a flake with a
timer attached. `video_export_save_test.dart` slept a flat `200ms` for a `VideoEdited` fan-out
(hash isolate + file move) and then read the DB row. Instrumented, that side effect takes
**452–536ms on an idle machine** — the budget was already short before CPU contention entered,
which is why the suite disagreed with itself run to run and why the failure count varied
instead of being one deterministic test.

The fix is a deadline poll, not a bigger sleep: loop until the condition holds or a generous
deadline (15s) expires, then fall through to the assertion so a genuine failure still reports
the real value rather than a timeout. `waitForHash` in that same file was already the pattern —
the flaky case simply never adopted it. **When you see a bare `delayed` before an `expect`,
treat it as a defect, not a wait.** A sleep encodes a guess about machine speed into the suite;
a poll encodes the condition you actually care about.

The mirror case is a test that *cannot* fail: `computeHashWithProgress` waited on a `ReceivePort`
whose isolate had died, so a missing source hung the runner rather than reporting. Give a test
whose failure mode is an indefinite wait an explicit `timeout:` — there the deadline **is** the
assertion, and a 10s red beats a 30s framework timeout that names no unit.

## Ask which direction load pushed the behaviour

Not every flake is a budget that ran out. `sync_diagnostics_test.dart` asserted `ORPHAN h1` where
a loaded run produced `ORPHAN h2`: `AssetManifestDao.getAll()` orders `importedAt DESC`, and the
fixture stamped every row `DateTime.now()` microseconds apart, so the assertions held only while
two inserts landed inside one clock tick and SQLite fell back to rowid order. Load *separated* the
timestamps and the real ordering asserted itself — **the flake was the fast path and the failure
was the code working.** Compare the deadline case above, where load stole time from a budget that
was already short; the two look identical from the outside and want opposite fixes. A test that
reads an ordered query must seed the ordering key deterministically: report order should be a
property of the fixture, never of clock resolution.

Both flakes were named the same way, and not by the compact reporter — `flutter test --reporter
json` filtered on `testDone`/`error` gives the failing test, its suite path, and the assertion
text, where `+1351 ~4 -1` gives a count and nothing to act on.

## A logger that reports a failure can replace it

`FlutterError.demangleStackTrace` is wired up by `testWidgets` and **not** by plain `test`.
`StageLogger.fail` calls `debugPrintStack`, which asserts at `stack_frame.dart:197`
(*"Got a stack frame from package:stack_trace, where a vm or web frame was expected"*) on the
traces that propagate inside a plain `test()` body. The resulting `_AssertionError`
**supersedes the exception under test**, so every error path that logs through `StageLogger`
reports the logger's own assertion instead of the cause — and `expectLater(..., throwsA(...))`
fails against a type nobody wrote.

This cost two sessions on one bug: the instrument meant to name the cause was overwriting it.
Root `CLAUDE.md` states the rule directly — *a diagnostic that truncates its own evidence is
the first bug to fix* — so when an error assertion fails against a type you never threw,
suspect the reporting path before the code.

**Fixed suite-wide, not per file.** `test/flutter_test_config.dart` wires the hook once:
`flutter_test` looks for the nearest file of that name above each test and runs its
`testExecutable(testMain)` instead of `main` directly, so anything set there applies to every
test under `test/` with no import — the only hook that can make a rule hold for tests that do
not exist yet. The production logger is unchanged, deliberately: `debugPrintStack` is correct
behavior, and bending it to a harness gap would trade a real diagnostic for a test-shaped one.
Red/green is in `test/core/utils/stage_logger_trace_test.dart`, which asserts from a plain
`test()` body that a `StageLogger`-reported cause is what the caller still surfaces.

## Testing a widget that reads a static buffer

`DiagnosticsLog`'s retained ring buffer is process-global static state, and its feed widget
polls it on a `Timer.periodic`. Both are the usual sources of cross-test bleed and the
repo's documented `Timer is still pending` flake (`docs/stale-tests-post-redesign.md`), so
the pattern that keeps `diagnostics_buffer_test.dart` and
`system_status_diagnostic_feed_test.dart` deterministic is worth stating:

- **Reset the global in `setUp`, never in `tearDown`.** `DiagnosticsLog.clearBuffer()` plus
  an explicit `configure(...)` means each case states the thresholds it depends on rather
  than inheriting whatever ran last.
- **Cancel the timer in `dispose`, and let the tester dispose the tree.** `testWidgets`
  tears the tree down at the end of each case, which cancels the periodic timer — no
  pending-timer failure, and no need for `fakeAsync`.
- **Pump the panel, not the screen.** `SystemStatusScreen` watches boot and storage
  providers that need the whole app graph; the claim under test is about the log buffer, so
  the feed is exposed as `SystemStatusScreen.debugFeed` (`@visibleForTesting`) and pumped
  alone. A narrower harness is the difference between a widget test and a boot test.
- **Assert the negative.** The feed previously rendered four hardcoded lines, so its test
  asserts the fiction is *absent* (`findsNothing`) as well as that real records appear —
  a placeholder that still renders would otherwise pass a purely positive assertion.

## A conditional export hides half its branches from the suite

`flutter test` runs on the Dart VM, so every `if (dart.library.js_interop)` export resolves to
its **native** branch. The web branch is not merely untested — it is never compiled by the
suite at all. The blind spot is structural, and it reads as the opposite of a blind spot,
because the branch that *does* run is green.

`lib/dev/preview_db.dart` is the worked example. It exports `preview_db_native.dart` or
`preview_db_web.dart`; `test/preview_harness_smoke_test.dart` exercises the harness end-to-end
and passes, proving the native executor seeds and streams. Meanwhile `preview_db_web.dart` —
the only file touching `WasmSqlite3`, the VFS registration, and the `rootBundle` asset key —
sat broken through a green suite: it never registered a virtual file system, so every web
preview died with `SqliteException(1): no such vfs: ` before a single row was read
(`add-web-first-release-and-monetization` 1.0.6).

The trap is that the green native test actively *misdirected* the diagnosis. "Native path
proven clean" plus "web dead" was read as evidence about the wasm binary and the v28 `onCreate`
SQL, when the two branches simply share no code. Two rules follow:

- **A conditional export needs a gate per branch, or the untested branch must be named as a
  gap.** `flutter test --platform chrome` compiles the web branch; where that is impractical,
  say so in the ledger rather than leaving the asymmetry implicit.
- **When one platform fails and another passes, the passing test is not evidence about the
  failure.** Check whether the two even share an execution path before reasoning across them.
  This is the same lesson Android taught on 2026-07-28, one layer down.

## Known-pre-existing-failures policy

Not every red test is your bug. The suite carried a documented set of failures belonging to a **test-ahead** change (`clarify-review-loop-and-media-cleanup`) plus post-redesign staleness — tests describing an implementation or copy that no longer matches. That set has since been **quarantined in place**: the affected cases (`rename_magic` / `video_export_save` path-scheme asserts, `card_count_sync` FSRS counts, `stats_screen` copy, flaky `party_screen` timers, …) now carry explicit `skip:` markers pointing at the ledger `docs/stale-tests-post-redesign.md`, so a clean run of the suite is green rather than "green modulo a memorized red list". Un-skipping one is the work order to reconcile the test with the shipped behavior, recorded in that ledger.

**The policy:** documented pre-existing failures are recorded and **not chased** while working an unrelated change. Before assuming a red test is pre-existing, *re-baseline*: stash-and-rerun to confirm it fails on clean `HEAD` too. A failure that is red on your branch but green on clean `HEAD` is your regression — that one you own. The discipline is what keeps binary truth honest: "the suite has failures" is not license to ignore *new* red, only known-baseline red.

## Standards this chapter enforces

- No success claim without terminal-verified proof; "compiles" / "analyzes" / "200" is not "works". ([`#test-1`](./09-standards.mdx#test-1))
- Bug fixes follow red/green: failing repro (`exit 1`) → smallest fix → same repro green (`exit 0`). ([`#test-2`](./09-standards.mdx#test-2))
- Runtime/visual verification runs on the iOS simulator; macOS is a non-target, and Chrome is a compile/boot check, not the canonical proof surface. ([`#test-3`](./09-standards.mdx#test-3))
- Pre-existing failures are re-baselined by stash-and-rerun and left unchased; new red on your branch is yours. ([`#test-4`](./09-standards.mdx#test-4))
